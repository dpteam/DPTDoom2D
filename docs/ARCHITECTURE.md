# Архитектура

## Два слоя и одна граница

```
┌──────────────────────────────────────────────────────────┐
│  Game/          геймплей: мир, игрок, монстры, оружие     │  ← перенос 1:1 из C
│                 предметы, двери, эффекты, меню, сейвы    │
├──────────────────────────────────────────────────────────┤
│  Engine/        платформенный слой                        │  ← переписан под C#
│                 WAD · VGA-фреймбуфер · палитра · ввод ·   │
│                 звук · музыка · сохранение структур       │
├──────────────────────────────────────────────────────────┤
│  FNA (external/fna)  XNA 4.0 API → SDL2/FNA3D/FAudio      │
└──────────────────────────────────────────────────────────┘
```

Граница проходит ровно там, где в оригинале были `vga.h`, `files.h`, `sound.h`
и `keyb.h`. Всё, что выше, — построчный перенос C-кода; всё, что ниже, — новый
код под платформу.

## Ключевое решение: рендер остался программным

Doom2D рисует в 8-битный палитровый фреймбуфер 320×200. На индексах палитры
завязано буквально всё:

| Что | Как в оригинале |
|---|---|
| затенение по расстоянию и урону | `clrmap[12][256]` — замена индекса по таблице |
| дым | `mixmap[256][256]` — смешение двух индексов |
| огонь | `flametab[16]` |
| цвет игрока | индексы `0x70..0x7F` перекрашиваются на лету |
| вода | индекс не рисуется, а тонируется colormap'ом поверх фона |

Перевести это на «нормальные» текстуры со спрайт-батчем — значит переписать
всю графику и потерять совпадение с оригиналом. Поэтому:

```
Vga.Buffer (byte[], 320×200)  ──палитра──▶  Color[]  ──SetData──▶  Texture2D
        ▲                                                              │
        │                                                              ▼
   Vga.Spr / Vga.Clr / Vga.Pic                              SpriteBatch, PointClamp,
   (построчный перенос из vga.c)                            целочисленный масштаб ×2
```

Один блит на кадр. Оригинал на DOS удваивал пиксели в окно 640×400 — мы делаем
то же самое `PointClamp`'ом.

Побочный плюс: `--simulate` умеет отрисовать кадр без GPU и записать BMP, чем
и пользуются тесты и генератор картинок для документации.

## Что пришлось решать по-другому

**Указатели → объекты.** В C `void *p` — это одновременно «залоченный ресурс» и
«указатель на `vgaimg`», а `((int*)p)[-1]` даёт номер ресурса. В C# это
`Res.Locked` (номер + байты + ленивый `VgaImage`), поэтому `Z_sound(p, v)` и
`Vga.Spr(x, y, img)` читаются как в оригинале.

**`keys[SDLK_*]`.** Игровая логика в C индексирует массив клавиш SDL-keysym'ами.
Вместо того чтобы размазывать `KeyboardState` по всему геймплею, `Kbd` один раз
за кадр переводит XNA-клавиши в keysym'ы. В результате `player.c` и `menu.c`
переносятся почти без изменений.

**Сохранения.** Оригинал пишет сырые структуры `#pragma pack(1)`. Здесь те же
поля пишутся по одному через `BinWriter`/`BinReader` — формат остаётся
байт-совместимым (`ver=3`), но без `unsafe` и маршаллинга.

**Анимации монстров.** В C `char *ap` — указатель на строку кадров; в сейв он
попадает как адрес. Здесь анимация опознаётся по содержимому и восстанавливается
по индексу, иначе загрузка сохранения ломалась бы.

**Порядок инициализации.** `G_init` в оригинале грузит ресурсы, которые нужны
`M_startup`; в C# статические конструкторы и `Init()` вызываются явно в том же
порядке, что в `main.c`.

## Поток одного тика

```
Kbd.Update()            клавиши → keys[]
Menu.Act()              меню/читы; если меню открыто — тик заканчивается
World.Act()             анимация стен
Items / Switches        подбор, двери
Player.Act()            движение, стрельба, смена оружия
Monsters.Act()          AI, стрельба, смерть
Bmap                    перестройка блочной карты
Weapons / Dots / Smoke / Fx
Player.Damage()         применение накопленного урона
```

20 тиков в секунду (`DELAY 50`) — ровно как в DOS-версии, поэтому тайминги
анимаций, скоростей и звуков совпадают.
